## 3. 各竞品详细分析

### 3.1 FFmpeg（行业标准）

**优势**：
- 支持几乎所有音视频格式和编解码器
- 高性能 C/汇编实现，含 SIMD 优化
- 丰富的滤镜库（libavfilter）
- 活跃社区，持续更新

**劣势**：
- C 语言，.NET 集成需要 P/Invoke 或进程调用
- LGPL/GPL 许可证可能有限制
- API 复杂，学习曲线陡峭
- 无 IoT 专用适配

**对 NewLife.Video 的启示**：
- 复杂编解码委托给 FFmpeg 是务实选择
- 需要提供比 FFMpegCore 更简洁的 .NET API
- 纯托管部分（容器/帧处理/流协议）可差异化

### 3.2 FFMpegCore（.NET 最流行封装）

**优势**：
- 流式（Pipe）API，避免临时文件
- 运行时自动下载 FFmpeg 二进制
- 流畅的参数构建器
- 活跃维护

**劣势**：
- 纯进程封装，无任何纯托管实现
- API 粒度粗，面向转码而非帧级操作
- 无 IoT/芯片头/ONVIF 等场景支持
- 错误处理依赖 ffmpeg stderr 解析

**对 NewLife.Video 的启示**：
- 借鉴其流式 Pipe API 设计
- 在帧级操作（逐帧解码/编码/处理）上做出差异化

### 3.3 ImageSharp（纯托管图像标杆）

**优势**：
- 纯托管，零原生依赖
- 高性能（SIMD 加速）
- 完善的 JPEG/PNG/GIF/WebP 编解码
- 优秀的 API 设计

**劣势**：
- 仅图像，不支持视频
- SixLabors Split 许可证（商业需付费）
- 无流媒体/设备/IoT 功能

**对 NewLife.Video 的启示**：
- MJPEG（逐帧 JPEG）可直接借鉴其 JPEG 算法思路
- YUV↔RGB 转换可参考其色彩管线设计
- 纯托管优先的策略值得遵循

### 3.4 OBS Studio（采集/编码/推流最佳实践）

**优势**：
- 完整的采集→编码→推流→录制管线
- 多平台支持（Win/Mac/Linux）
- 丰富的插件生态
- 久经实战验证的架构

**劣势**：
- C/C++，非 .NET 库
- 作为应用而非库，嵌入困难
- 体积庞大

**对 NewLife.Video 的启示**：
- 参考其插件式架构设计
- 参考其采集后端抽象（DirectShow/V4L2/AVFoundation）
- 参考其编码参数默认值

## 4. NewLife.Video 差异化定位

### 4.1 核心优势

| 优势 | 说明 |
|---|---|
| **纯托管 + FFmpeg 混合** | 简单场景（MJPEG/YUV转换/容器解析/帧处理）零依赖；复杂编解码委托 FFmpeg |
| **IoT 深度适配** | ONVIF 设备发现、GB/T 28181 协议、海思/大华/宇视芯片视频头、录像计划管理 |
| **NewLife 生态集成** | 复用 NewLife.Net（RTSP/RTMP）、NewLife.Core（日志/配置/序列化）、NewLife.IoT（设备规范） |
| **帧级 API** | 不限于文件转码，提供逐帧解码/编码/处理能力，适合实时视频流 |
| **跨平台** | netstandard2.0+，Windows/Linux/macOS 全覆盖 |
| **中文优先** | 文档、注释、错误信息均为简体中文，降低国内开发者门槛 |

### 4.2 目标用户

- **IoT 视频监控开发者**：摄像头 RTSP 拉流 → 解码 → 截图/录像/推流
- **视频处理工具开发者**：视频转码、剪辑、水印、格式转换
- **实时通信系统开发者**：WebRTC/RTMP 视频管线

### 4.3 与 FFMpegCore 的差异化

| | FFMpegCore | NewLife.Video |
|---|---|---|
| 抽象层级 | 进程调用封装 | 纯托管 + 进程调用混合 |
| 帧级操作 | 仅通过 Pipe | 原生 `VideoFrame` + 处理管线 |
| IoT 协议 | 无 | ONVIF/GB28181/芯片头 |
| 纯托管容器 | 无 | MP4/FLV/AVI/TS 骨架 |
| 处理管线 | 依赖 ffmpeg 滤镜 | 纯托管 `IVideoProcessor` 管线 |
| 运动检测 | 无 | 内置 |

## 5. 技术选型参考

### 5.1 编解码层

- **纯托管 MJPEG**：参考 ImageSharp 的 JPEG 编解码算法，实现基线 DCT Huffman
- **H.264/H.265 解码**：FFmpeg 进程管道 (`ffmpeg -i pipe:0 -f rawvideo pipe:1`)
- **H.264/H.265 编码**：FFmpeg 进程管道 (`ffmpeg -f rawvideo -i pipe:0 -c:v libx264 pipe:1`)
- **YUV↔RGB 转换**：纯托管，SIMD 加速（`System.Numerics.Vector`），参考 FFmpeg libswscale 公式

### 5.2 容器层

- **MP4/FLV/AVI/TS 读取器**：纯托管解析盒/标签结构，提取裸流
- **MP4/FLV 写入器**：纯托管写盒/标签，配合 FFmpeg 编码
- **工厂模式**：扩展名 + 魔术字节双重路由

### 5.3 流媒体层

- **RTSP 客户端**：基于 `NewLife.Net` 的 TCP/UDP Socket，实现 RTSP 信令 + RTP 接收
- **RTP 封包/解包**：纯托管，H.264 FU-A (RFC 6184)、H.265 (RFC 7798)
- **RTMP 推流**：基于 `NewLife.Net` 的 TCP 连接，实现 RTMP 握手 + FLV 流推送

### 5.4 IoT 层

- **ONVIF**：WS-Discovery (UDP 组播) + SOAP/XML 设备服务调用
- **GB/T 28181**：SIP 注册/信令 + RTP 媒体流，基于 `NewLife.Net`

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| FFmpeg 许可证 (LGPL/GPL) | 法律合规 | 仅通过进程调用（非链接），用户自行安装 FFmpeg |
| FFmpeg 版本兼容性 | 命令行参数差异 | 版本检测 + 参数适配矩阵 |
| 视频编解码性能 | 进程间管道开销 | 共享内存优化；后续考虑 P/Invoke 直接调用 libavcodec |
| 纯托管容器解析不完整 | 部分 MP4 文件无法解析 | 回退到 FFmpeg 容器解析 |
